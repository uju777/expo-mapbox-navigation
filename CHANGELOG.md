# Changelog

## Unpublished

### 🛠 Breaking changes

### 🎉 New features

- Add the `voiceUnits` prop (`"imperial"` or `"metric"`) to set the unit of the spoken distances independently of the locale ([#31](https://github.com/uju777/expo-mapbox-navigation/issues/31)).
- Config plugin (Android): the `accessToken` option is now also written to the `mapbox_access_token` string resource. The Mapbox SDK falls back to that resource when no token has been set in code, so the view can be created without waiting for `Mapbox.setAccessToken()`. If another file in `res/values` already defines the resource, the plugin leaves it alone and prints a warning.
- Config plugin: print a warning when the `accessToken` option starts with `sk.` (a secret token). The option is stored in the app on both platforms.

### 🐛 Bug fixes

- Android: the route request now sets `voice_units`. Without the `voiceUnits` prop it is derived from the `locale` prop: imperial for the countries `US`, `LR` and `MM`, metric otherwise. The parameter was not set before, so the Directions API default (imperial) was used regardless of the locale. This changes the spoken unit for every locale outside those three countries, for example `en-GB` or a locale without a country such as `en`; set `voiceUnits="imperial"` to keep the previous unit.
- Android: `onRouteFailedToLoad` is now called when a Map Matching request fails (`useRouteMatchingApi`). The failure was ignored before.
- Android: when the view cannot be created because no access token is set, a message that names the missing token is written to logcat. When the JavaScript bundle runs in development mode (`__DEV__`) and expo-modules-core provides `AppContext.errorManager`, the message is also reported to the JavaScript console. In release builds it is only written to logcat.
- Android: a `MapboxNavigationView` now attaches the activity to `MapboxNavigationApp` when it is created instead of relying on the module having done so. The module attaches the activity from a coroutine when the activity enters the foreground. A view that was created before that coroutine had run kept a `null` `MapboxNavigation`, and its route request was skipped without an error (the observer registrations are guarded by the same null check). This is not new in this release; the test notes below say how often it happened with 1.6.4.
- Android: the route line is now rendered when the routes arrive before the map style has loaded. The route line data was handed to the route line view only if the style had already loaded at that moment. Otherwise it was dropped and not rendered later: in one drive the route line was missing from the first to the last screenshot while the maneuver arrow, the location puck and the instructions were shown. The data is now handed over through `MapboxMap.getStyle`, which calls back at once when a style is loaded and otherwise when the style has loaded. The replaced statement is the same in 1.6.4, so this is not new in this release. It was observed with the code of this release before the change; the test notes below say how often.
- Android: add consumer R8 rules (`android/proguard-rules.pro`): two `-dontwarn` rules for the AutoValue annotation classes that the Mapbox Java models reference. With 1.6.4, a release build of our Expo 54 test app with minification enabled stopped in R8 with `Missing class com.google.auto.value.AutoValue`. With the rules the build completes, and the app starts and sends the route request. With a real token the route was loaded in one start of a minified build; that build was made before the route line change (see the test notes below).
- iOS: `max_height` and `max_width` are only added to the route request when `vehicleMaxHeight` / `vehicleMaxWidth` are set. The request was built with `0.0` for a missing value before.

### 💡 Others

- Android: changed props are applied in one update after each render instead of one update per prop.
- Add tests for the config plugin (`yarn test`) and a GitHub Actions workflow that builds the module and runs them.

_How this was tested: on Android with Expo 54, `@rnmapbox/maps` 10.1.44 and a placeholder access token, on an emulator, with the New Architecture disabled and enabled. Debug and release builds of a test app whose first screen is the navigation view were built and started, and the route request URL and the events were read from logcat. No route was loaded in the runs of this paragraph because the token is not valid; the runs with a real token are described below. Release builds were built without minification, with R8 minification, and with minification and resource shrinking; the `mapbox_access_token` resource was still in the minified and shrunk APKs. The route request was sent in all 35 release starts of this version (20 with the New Architecture disabled, 15 with it enabled); in 17 of them the view attached the activity before the module did (16 and 1). It was also sent again after the activity had been recreated in a running process (3 runs, New Architecture disabled). With the published 1.6.4, in release builds without minification of the same app, which had a `mapbox_access_token` string resource, the request was missing in 4 of 10 starts with the New Architecture disabled and in 2 of 10 starts with it enabled. The JavaScript console report for a missing token was observed in debug builds; in release builds the message was only in logcat. The Android code was also compiled with Expo 53 and Expo 58. The iOS changes were compiled for the simulator in an Expo 58 test project and not run. The route line change of this release (one statement in the Android routes observer) was made after the runs in this paragraph. Of these runs only the Expo 53 and Expo 58 compilations were repeated with it; the runs made with the change are described in the last paragraph._

_Runs with a real access token before the route line change (release builds of the same test app on an emulator): the route was loaded in all seven starts, six with the New Architecture disabled and one with it enabled. In two of the six the view attached the activity before the module did. One start used `useRouteMatchingApi` (the Map Matching request returned 200) and one was a build with R8 minification; both were stopped after about 12 seconds without driving. Two starts, one with the New Architecture disabled and one with it enabled, were followed by a drive: positions along the 1.4 km route were fed through the Android gps test provider, one per second at 15 m/s, starting about 20 m from the position the emulator had reported before. In each drive 114 progress events reported the travelled distance from 0 m up to the route length, `onFinalDestinationArrival` was called once, no second route request was logged, and the app requested audio focus for navigation guidance and played nine MP3 clips. The emulator had no audio output, so nothing was listened to. In the New Architecture drive the map tiles and the voice clips arrived about 45 seconds after the route had been loaded: the first requests failed with `net::ERR_CONNECTION_CLOSED` or `net::ERR_QUIC_PROTOCOL_ERROR`, no request failed after that, and another app on the emulator reported the network as not working within four seconds of those errors. The text of five spoken instructions was read from the Voice API request URLs that those errors left in logcat; the one that contained a distance gave it in metres._

_Route line: three of those seven starts were first starts with empty app data on a new emulator, and the route line was missing in two of them: none of the six screenshots of the New Architecture drive shows it, and the log of one start with the New Architecture disabled has no line from the route line layer set-up (its screenshots show another part of the map). The change was then compared in first starts after clearing the app data (`pm clear`), in release builds without minification and with the default map style (the test app does not set `mapStyle`); each start was stopped about 8 seconds after it began. Without the change, with the New Architecture disabled, the route line was missing in 1 of 4 starts (the screenshot shows the map, the maneuver arrow, the puck and the instruction, and no route line). With the change it was drawn in 6 of 6 starts with the New Architecture disabled and in 1 of 1 with it enabled. A test-only build (the changed code plus two log statements, not the published package) was started twice with the New Architecture enabled: in one start the style had not loaded when the route line data was ready, the render call followed 59 ms later and the screenshot shows the route line; in the other the style had already loaded. The package with the change was then driven along the route once with the New Architecture enabled: 115 progress events were logged, `onFinalDestinationArrival` was called once, and the route line is in all five screenshots (four during the drive, one after the arrival). In that drive `onUserOffRoute` was called once, 2.1 seconds after the route had been loaded; the Navigation SDK requested a new route and the drive continued on it (1,408 m). The two earlier drives had no such event; their start script waited two seconds before starting the app, and the Navigation SDK logged the first position as 3.7 and 3.6 seconds old, against 1.6 seconds in this drive. To see whether the event depends on the route line change, six further starts were made with the New Architecture enabled and without that wait, alternating the package without the change and the package with it; in each start the first six positions of the track were fed and the app was stopped about 12 seconds after it began. The event occurred in 1 of the 3 starts without the change (1.9 seconds after the route had been loaded) and in none of the 3 starts with it. It therefore also occurs without the change; three starts of each package do not show whether the change affects how often it occurs. Its cause was not determined._

## 1.6.4 — 2026-11-16

### 🎉 New features

- The config plugin now warns during `expo prebuild` when the installed `@rnmapbox/maps` or the configured `mapboxMapsVersion` is outside the tested combination.

### 🐛 Bug fixes

- Android: the Gradle script of this module no longer fails to configure with Android Gradle Plugin 9 built-in Kotlin. The `kotlin-android` plugin is only applied when AGP has not registered the `kotlin` extension ([#44](https://github.com/uju777/expo-mapbox-navigation/pull/44) by [@gabrieldonadel](https://github.com/gabrieldonadel)), and `kotlinOptions` is only configured when that plugin is applied.
- Types: import `ViewStyle` and `StyleProp` from `react-native` instead of `react-native/types`. The old path does not exist in newer React Native versions (verified on 0.88), which silently typed the `style` prop as `any`.
- Config plugin: on iOS, throw a clear error when the `mapboxMapsVersion` option is missing instead of writing `'undefined'` into the Podfile.
- Config plugin: the Podfile patch can now run more than once on the same Podfile without duplicating its lines, and a changed `mapboxMapsVersion` is no longer overridden by a stale line.
- iOS: remove the podspec reference to a `Turf.xcframework` that is not part of the package, and point the podspec source at the current repository.

### 💡 Others

- README: add a compatibility table, explain how to set the access token on Android, and document `initialLocation`, `followingZoom`, `onRouteFailedToLoad`, the `onRoutesLoaded` payload and the `recenterMap()` ref method.
- `.npmignore`: exclude local files (`CLAUDE.md`, `android/.gradle`, `yarn.lock`) so that they cannot end up in the npm package.
- Remove `package-lock.json`. The repository uses yarn, and the stale npm lock file made `npm ci` fail.
